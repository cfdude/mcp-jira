# Development Workflow — OpenSpec + Superpowers (two review gates)

This project codifies a spec-driven workflow with **two mandatory third-party
code-review gates**. All new, non-trivial work — features, behavior changes,
multi-file refactors — flows through it. Trivial one-line fixes and pure chores
(dependency bumps, formatting) are exempt.

The reviewer at each gate is a **fresh-context Superpowers subagent**: it sees
the work product, not the session history, so it functions as an independent
third-party audit.

## The pipeline

```
/opsx:propose ──▶ 🚦 GATE 1 ──▶ /opsx:apply ──▶ 🚦 GATE 2 ──▶ docs ──▶ /opsx:archive
   (spec)        spec review     (build, TDD)    impl review   accept     (sync specs)
```

### 1. Propose — OpenSpec
Run `/opsx:propose "<idea>"`. Generates `openspec/changes/<change-id>/`:
`proposal.md`, `design.md`, `specs/*.md`, `tasks.md`. Then validate:

```bash
openspec validate <change-id> --strict
```

### 2. 🚦 Gate 1 — spec review (Superpowers, BEFORE any code)
Invoke the `superpowers:requesting-code-review` skill against the change
artifacts. They are uncommitted markdown, so point the reviewer at the **file
paths**, not a git SHA range. The review checks:

- Spec testability — every requirement has WHEN/THEN scenarios
- Cross-capability consistency and data-model correctness
- Fidelity to the existing code the change must integrate with
- Task ordering and TDD compliance

Fix **Critical + Important** findings in the specs, then re-run
`openspec validate <change-id> --strict`. **Do not `apply` until the spec is
clean.**

### 3. Apply — OpenSpec
Run `/opsx:apply`. Implement each task with TDD (RED → GREEN → REFACTOR) and
**one conventional commit per task** — never batch tasks into a single commit.
Per-task quality fix-ups are autonomous; they don't need a check-in.

### 4. 🚦 Gate 2 — implementation review (Superpowers, AFTER commits, BEFORE docs)
Once **all** tasks are implemented and committed — but **before any
documentation changes** — invoke `superpowers:requesting-code-review` against
the full committed diff (`BASE_SHA..HEAD_SHA`). The review checks:

- Alignment with the proposal/specs
- Tests actually pass; error and edge handling
- Security and migration correctness
- The STDIO **stdout/JSON-RPC invariant** (stdout carries only JSON-RPC)

Fix **Critical + Important** before writing docs. Note **Minor** findings; push
back with reasoning if the reviewer is wrong.

### 5. Acceptance + docs
Only after Gate 2 is clean: update docs / README / CHANGELOG.

### 6. Archive — OpenSpec
Run `/opsx:archive <change-id>`. Syncs delta specs into `openspec/specs/` and
moves the change to `openspec/changes/archive/`. **Never skip** — archived specs
are how the next session knows the feature exists.

## Gate rules

- **Critical → fix now. Important → fix before proceeding. Minor → note.**
- A gate is not "done" until you re-validate / re-test after applying fixes.
- Both gates are mandatory; never proceed past one with unfixed Critical or
  Important findings.

## Definition of done

Tests pass (unit + integration), `npm run lint` reports 0 problems, Prettier is
clean, `npm run build` is green, and MCP behavior is verified with
`npm run inspector`.

## Tooling notes

- Project context for artifact generation lives in `openspec/config.yaml`.
- The `/opsx:*` commands and `openspec-*` skills are generated by `openspec init`
  into the **gitignored** `.claude/` directory. Each clone runs init once:

  ```bash
  openspec init --tools claude   # first-time setup
  openspec update                # refresh instruction files
  ```
